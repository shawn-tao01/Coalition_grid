Check of resilience/method.tex against the code (MPC_optimiser.jl, Coalition.jl), 2026-10-14.
Assumes RESIL.enabled = true (the default) and, for the outage parts, OUTAGE.enabled = true, as in
resilience/test_three_buildings.jl. Only places where the two are not exactly the same are listed.


A. The problems (Section 1)

1. Horizon length. The tex uses a fixed K (k = 0..K-1). The code shortens the window at the end of the data to
   min{K, T - t + 1} steps (single_optimise, MPC_optimiser.jl:113-117; the same in single_optimise_outage and in
   the formation, Coalition.jl:769-770). The last steps of the day are solved over fewer than K steps.

2. Last step of the window. The code has a constraint that is in neither (R1) nor (R3):
       u^c_i(t+K-1) - u^d_i(t+K-1) >= -SoC_i(t+K-1)      (final_delta_c, MPC_optimiser.jl:162 and :235)
   Conversely, (R1c) written for k = 0..K-1 defines SoC_i(t+K), which the code does not have: its state
   variables stop at t+K-1, and (R1e) also bounds them only up to t+K-1.

3. Reserve window (R2). The code cuts the sum over m at the end of the forecast row, 96 steps ahead
   (MPC_optimiser.jl:48), so near the end of the forecast fewer than tau steps are summed. (R2) always sums
   m = 1..tau.

4. epsilon in (R3). The tex only requires epsilon > 0. To stop the plan from charging and discharging at once
   instead of curtailing, it must hold that epsilon > c^curt (1 - eta^c_i eta^d_i) (code comment,
   MPC_optimiser.jl:37). The defaults satisfy it: c^shed = 1, c^curt = 0.1, epsilon = 0.05.


B. Algorithm 1 (resilience_focussed_coals, Coalition.jl)

5. Line 8. The tex skips a merge if r < 0; the code skips it if r < -1e-3 (RES_TOL, Coalition.jl:794).

6. Line 9. The code also skips a candidate whose solve fails, V = Inf (Coalition.jl:801). The tex has no such
   skip: in the resilience phase such a merge could still be accepted, because mu does not depend on the solve.
   A failed solve is detected only through NaN values (plan_cost, Coalition.jl:717); the solver status is not
   checked.

7. Line 12. The tex requires val > 0; the code requires val > 1e-6 (VAL_TOL, Coalition.jl:809).

8. Line 9. The code solves each distinct merge only once per step t and reuses it in later rounds and in the cost
   phase. This gives the same result as solving it again.

9. Outage line. The tex defines V as the optimal value of (R1). During an outage the code's V, and hence val, is
   the optimal value of (R3) (shedding and curtailment cost). The outage line no longer states this.


C. Algorithm 2 (coal_MPC, MPC_optimiser.jl:602-680)

10. Line 4. The code sets SoC_i(t+1) = max{0, planned SoC_i(t+1|t)} (MPC_optimiser.jl:639, :657). The floor at 0
    is not in the tex. If the plan is NaN (failed solve), the code keeps SoC_i(t+1) = SoC_i(t).

11. Realised cost (Line 5). The code computes the realised grid exchange from the realised data,
        G^tot_i(t) = d_i(t) - g_i(t) + u^c_i(t) - u^d_i(t) - C^tot_i(t)     (MPC_optimiser.jl:642, :659),
    books [G^tot_i(t)]^+ as bought and [-G^tot_i(t)]^+ as sold, and prices them with P^buy(t), P^sell(t)
    (:672-678). Algorithm 2 no longer states this, so the "realised cost R(C_j(t))(t)" of Line 5 is not defined
    in the tex: Section 2 defines R as the planned first-step cost. If the plan is NaN, the code sets the realised
    exchange to 0, so that building's load at that step is not paid for.

12. Outage. During an outage the code books the realised imbalance as d^shed_i(t) = [G^tot_i(t)]^+ and
    g^curt_i(t) = [-G^tot_i(t)]^+, with no grid trade (MPC_optimiser.jl:644, :661). Line 7 of the tex returns the
    totals of d^shed and g^curt, but no line defines them.


D. Same result, different representation in the code

13. One free variable coal_exch = -C^tot_i per building and step instead of C^buy_i, C^sell_i >= 0; the state
    SoC_i(t+k) is a variable with (R1c) as equality constraints; delta_s = u^c - u^d is an extra variable.
14. Coalitions are solved centrally (single_optimise). ADMM would be used only with RESIL.enabled = false.
15. SCS solves to about 1e-4, so V, val and R are accurate to about that.


E. Inconsistencies inside method.tex found during the check

16. Table: d_i, g_i, SoC_i, u^c_i, u^d_i, R({i}) and G^tot_i are described as "of coalition i", but in (R1) and in
    the code i is a building. s~ is indexed by a coalition in (R2) (s~_{C_j}) but by i in the table.
17. Table: G^tot_i has two rows with different wording ("net energy exchanged with the grid" and "net energy
    coalition i buys from the grid, G^tot_i = G^buy_i - G^sell_i").
18. The size limit is \mathcal{C}_max in the table and in Algorithm 1 Line 7, but C_max in the text after (R7).
19. Text after Algorithm 2: "realised cost ... (Line 6)" and "SoC_i(t+1) is passed to the next step (Line 7)";
    in the current Algorithm 2 these are Lines 5 and 6.
20. Typos: "The lower bound of the SoCis calculated", "itranks", "load shedded".
